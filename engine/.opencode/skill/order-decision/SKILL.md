# 接单决策 SKILL

## 职责

基于现金流状态和报价合理性，给「接/不接」的建议和理由。

## 输入

用户描述的一笔潜在订单：报价金额、预计工时、客户情况（可选）。

## 输出格式

```json
{
  "decision": "接|不接|再考虑",
  "reasons": ["理由1", "理由2"],
  "min_price": 最低建议报价,
  "risk": "主要风险"
}
```

## 规则

1. 先查现金流状态（调用 get_cashflow_status 工具），若现金流缺口存在则提示资金压力
2. 报价低于「时薪 × 预计工时」时建议「再考虑」或提价
3. 给 2-3 条理由，每条可追溯到输入或现金流数据
4. 只给建议和理由，最终决定权在用户

## 与产品运行时的关系（2026-09-28 补，防止「文档说有、代码没有」）

本 SKILL 上面那套是**编排层（引擎层）的方法论**：由 opencode 按需加载、可 spawn 专家子代理做多视角审议（留痕见仓库 `08-实测/多智能体子代理并行审议-实测留痕-20260928.md`）。

**产品运行时另有一条确定性实现**，已落地为 HTTP 端点，两者输出契约兼容（本 SKILL 的 `{decision, reasons, min_price, risk}` 被完全覆盖）：

- `POST /api/decision`，入参 `{amount_cents, estimated_hours, deliver_days?, counterparty?, tax_rate?, platform_rate?}`
- 历史时薪**由账本反推**（近 3 个月带工时收入的中位数 ÷ 总工时），不需要用户填时薪
- 三道闸门：`cash_runway`（现金流垫底）/ `receivable_cycle`（回款周期，含假设检验的偏差纠偏）/ `after_tax`（税后真实到手）
- 报价下限 = 历史时薪 × 预估工时 × (1 + 税负率 + 平台抽成)；推荐 / 上限的 1.10 / 1.25 是**经验系数、无文献出处**
- 口径纪律：数值全部由本地账本与状态引擎计算，**LLM 不参与数值**；缺「带工时的收入记录」时如实返回 `insufficient`，**不给**假装精确的报价下限
- 测试：`09-代码/tests/test_decision.py`（golden case A-F + 确定性）
